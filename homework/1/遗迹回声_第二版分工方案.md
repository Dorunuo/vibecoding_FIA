# 《遗迹回声》第二版五人分工与并行 Vibecoding 方案

> **文件性质：团队执行版。**本方案替代《遗迹回声_五人分工方案.md》中的 Godot 路线与旧分工。旧文件只保留作讨论记录，不再作为开发依据。
>
> **唯一技术路线：HTML + CSS + JavaScript + Three.js。**不使用 Godot，不使用 GDScript，不把 Godot Web 导出当作 Three.js 的替代品，不要求使用 Blender 或 UE5。
>
> **团队真实情况：五位成员的技术水平接近，都不是以传统手写代码为主，而是主要通过向 AI 提供提示词、运行结果、继续追问和修正来完成游戏，即 Vibecoding。**因此，本方案不以“某位成员是资深架构师”为前提，而是通过严格文件边界、先冻结接口、小步生成、实际运行和统一验收来降低并行开发风险。
>
> 若本方案与课程作业原文冲突，以 `Week_05_Group_Assignment.md` 为最高依据；游戏设计细节可参考 `AI_HANDOFF_PROMPT.md`，组织分工和模块接口以本文件为准。

## 一、方案的核心结论

### 1. 三人核心开发组可以同时开发，但不是各写各的最后硬拼

三人分别负责：

- **A：场景环境、项目骨架与最终集成；**
- **B：输入、角色控制、第三人称相机与角色程序动画；**
- **C：宝物、陷阱、出口、游戏状态、UI、音效与 Demo。**

三人可以同时在各自分支或工作区中使用 AI 编码，但必须先共同确认并冻结本文件的接口契约。**AI 可以辅助诊断集成问题，但不能把“最后让 AI 自动猜着拼接”当作项目计划。**

### 2. 另外两人不是闲置人员，也不临时插入核心代码

- **D：视觉资源与素材合规负责人。**准备原创视觉规范、程序化建模参考、可选本地素材、音效来源和素材清单；灰盒版本优先，不以精细建模阻塞程序开发。
- **E：质量、试玩与交付负责人。**维护测试清单、组织每人实机检查、协调外部试玩、管理提交材料和视频流程；NO AI 内容必须由团队亲自记录。

### 3. 先跑通最小闭环，再增加美术和可选功能

优先顺序固定为：

```text
能启动 → 能控制 → 能收集 3 个宝物 → 能开门并胜利
→ 能失败和重开 → 有声音和音量控制 → Demo 能自动完成真实流程
→ 外部试玩与两轮改进 → 视频和提交 → 可选美化
```

## 二、课程硬性要求与本项目扩展必须分开

以下区分防止团队把扩展功能误当作最低要求，也防止遗漏真正的必交项。

| 项目 | 性质 | 本方案要求 |
|---|---|---|
| HTML、CSS、JavaScript、Three.js | 课程硬性要求 | 必须用于核心游戏，不可换成 Godot/GDScript |
| 真实 3D 场景、合适相机、玩家控制或有效互动 | 课程硬性要求 | P0 |
| 明确目标、可见进度或结果反馈、开始/重开路径 | 课程硬性要求 | P0 |
| 一个完整关卡，能在 5 分钟内演示完整循环 | 课程硬性要求 | P0；完整游戏也可以不超过 5 分钟 |
| 可听见的游戏反馈、方便的音量或静音控制 | 课程硬性要求 | P0 |
| 菜单明确的 Demo/Watch Demo 按钮 | 课程硬性要求 | P0；一键自动运行，无后续玩家输入 |
| Demo 使用真实游戏而非预录视频 | 课程硬性要求 | 必须复用正常移动、互动、计数、开门和胜利逻辑 |
| Demo 有声音、可退出/重启、结束后能回到人工游玩 | 课程硬性要求 | P0 验收项 |
| 本地可运行，不依赖实时 AI、账号、远程后端或外部服务 | 课程硬性要求 | 所有运行资源随项目提交 |
| 每人有具名贡献且每人亲自运行至少一次游戏检查 | 课程硬性要求 | E 建立五人检查记录 |
| 至少一名组外测试者试玩 | 课程硬性要求、NO AI | E 协调，团队亲自观察和记录 |
| 两轮真实改进记录，至少一轮来自外部试玩 | 课程硬性要求、NO AI | 团队亲自填写，不由 AI 生成或润色 |
| 每人一份不超过 200 词的学习总结 | 课程硬性要求、NO AI | 每人独立撰写 |
| 不超过 5 分钟的小组 MP4，含真人游玩、游戏内 Demo 和改进证据 | 课程硬性要求 | E 统筹，全组配合 |
| 三个掩埋晶体、两个陷阱、出口开启 | 原游戏提案内容 | 保留为本项目 P0 设计目标，但不误判为课程通用要求 |
| 键盘和鼠标 | 本项目基本操作 | P0 |
| Gamepad API 手柄支持 | 原提案扩展 | P1；只有真实设备测试过才能写“已验证” |
| 全部 jump/fall/land/hurt/victory 等动作 | 原提案扩展 | P1；最低版本优先保证 idle/walk 或 run/collect |
| 冲刺、复杂跳跃、精致服装、粒子、额外关卡 | 扩展 | P1/P2，不得阻塞 P0 |
| Blender 建模、外部模型、复杂骨骼 | 可选资源方案 | 非必需；优先 Three.js 几何体与程序动画 |

## 三、五人职责总览

> 角色按文件边界和交付责任划分，不代表能力高低。五人都可以使用 AI；谁拥有该任务，谁就必须运行、检查并解释自己保留的结果。

| 成员 | 角色 | 核心开发期职责 | 必须交付 | 每人亲自运行的最低检查 |
|---|---|---|---|---|
| A:陈致胜 | 场景环境、骨架与集成负责人 | 项目骨架、Three.js 渲染器、遗迹场景、静态碰撞、主循环、接口冻结、版本集成 | 可探索场景、可运行骨架、稳定集成版本 | 在新窗口启动游戏并确认场景、入口和出口可见 |
| B（姓名待填） | 角色与输入负责人 | 键盘/鼠标、角色移动、静态碰撞、第三人称相机、角色几何体和程序动画 | 可控制的角色、统一输入、角色动画 | 亲自完成 WASD、镜头、跳跃（若保留）及碰撞检查 |
| C（姓名待填） | 玩法、UI、声音与 Demo 负责人 | 三个宝物、陷阱、生命、出口、状态机、HUD/菜单、Web Audio、自动演示 | 完整玩法闭环、声音、真实逻辑 Demo | 亲自完成一次正常通关、一次失败/重开和一次 Demo |
| D（姓名待填） | 视觉资源与素材合规负责人 | 原创角色/遗迹视觉规范、配色、建模参考、可选本地素材、音效来源、素材说明 | 视觉规范、资源包或程序生成建议、素材来源清单 | 亲自检查角色四肢动作、宝物辨识度和出口可见性 |
| E（姓名待填） | 测试、外部试玩与交付负责人 | 测试矩阵、缺陷跟踪、外部试玩组织、README/报告/视频清单、提交复核 | 检查记录、真实反馈、交付包和提交确认 | 从提交副本按 README 独立启动，并检查操作、声音、重开和 Demo |

### 备份规则

- A 的备份为 A：至少会启动项目、定位场景资源和生成一个可运行版本。
- B 的备份为 B：至少理解输入帧和角色公开接口，能修复基础移动问题。
- C 的备份为 C：至少能检查游戏状态、宝物计数和 Demo 调用链。
- D 的备份为 D：能维护素材来源、文件命名和授权清单。
- E 的备份为 E：能按清单完成提交复核，但 NO AI 记录仍须由实际参与者亲自完成。

备份不等于两人同时修改同一文件；接管时必须明确交接文件所有权。

## 四、各成员详细任务与验收

### A：场景环境、项目骨架与最终集成

**主要任务**

1. 建立 `w05_3d_game/`、依赖清单、本地启动方式和基础页面。
2. 根据第五至七节建立全部模块骨架和可运行占位实现，形成“接口冻结版本”。
3. 创建 Three.js 场景、渲染器、灯光、雾、地面、墙、入口、遗迹区、机关区和出口静态门框；可开启门体及开门视觉由 C 负责。
4. 用简单几何体建立灰盒；在 `level.js` 中统一维护出生点、宝物点、陷阱区、出口和 Demo 路线。
5. 提供与可视墙体一致的静态碰撞盒，保证主路线宽度足够、不会无故卡死。
6. 拥有 `main.js`，按契约组合 A/B/C 模块，处理窗口缩放、动画循环和事件分发。
7. 每次集成保留一个可回退版本，不用 AI 一次性重写全项目来“解决冲突”。

**完成验收**

- 按 README 命令启动后无控制台模块加载错误。
- 场景明确是真实 3D，不是静态图片或纯飞越展示。
- 入口、三个宝物区域、障碍区和出口形成一条可完成路线。
- 视觉墙与碰撞墙基本一致；场景边界能阻止角色离开地图。
- A/B/C 任一模块暂时为占位实现时，骨架仍能启动并明确显示占位状态。

### B：角色、输入与第三人称相机

**主要任务**

1. 用 Three.js `Group` 和几何体制作原创低模女性探险者，包含头发、外套/探险服、围巾、背包、手套和靴子的可识别特征。
2. 建立左右手臂和腿部 pivot；至少实现 `idle`、`walk/run`、`collect`，跳跃保留时再实现 `jump/fall/land`。
3. 实现统一 `InputFrame`，键盘/鼠标不得产生另一套移动逻辑；P1 再接手柄。
4. 实现相对相机方向的 WASD/方向键移动、角色朝向、速度、加减速和简单重力/地面约束。
5. 使用 A 的静态碰撞盒处理墙体和边界；不直接修改宝物计数、生命、出口状态或 UI。
6. 实现第三人称跟随、鼠标环绕和适度平滑，避免相机穿墙造成严重遮挡；最低版本可使用简化相机碰撞。
7. 提供 `playAction()` 给 C 触发挖掘、受伤和胜利动作，但动作本身不改变游戏数据。

**完成验收**

- W 始终按当前相机朝向前进，左右移动和转向符合操作表。
- 角色不会明显穿过静态墙体或掉出关卡；重开后位置和姿态正确复位。
- 行走时四肢可见摆动，挖掘时有伸手/下蹲动作。
- 每帧输入中的 `Pressed` 字段只触发一次，不因按住按键反复收集或暂停。
- 手柄未实测时 README 明确写“未实测”，不能凭 AI 回答写“支持所有手柄”。

### C：玩法、UI、声音与 Demo

**主要任务**

1. 建立游戏状态：`MENU`、`PLAYING`、`PAUSED`、`WIN`、`GAME_OVER`，以及模式：`HUMAN`、`DEMO`。
2. 根据 `LEVEL.treasures` 创建三个部分掩埋的发光晶体，管理 `AVAILABLE → IN_RANGE → COLLECTING → COLLECTED`。
3. 靠近宝物显示“按 E 挖掘”；按键后调用 B 的 `playAction('collect')`，执行升起、变亮、旋转、计数和防重复领取。
4. 创建两个简单陷阱，可复用同一程序但具有不同位置、时序或形状；管理伤害、无敌间隔、失败和重开。
5. 实现“集齐 3 个宝物 → 出口开启 → 到达出口 → 胜利”，未集齐时到达出口须给出明确提示。
6. 实现菜单、HUD、目标提示、进度、生命、暂停、胜利、失败、重开、返回菜单和音量控件。
7. 使用 Web Audio API 或已授权本地音效提供收集、受伤、开门、胜利/失败等反馈；浏览器允许后再解锁声音。
8. 实现 Demo：根据 `LEVEL.demoRoute` 生成与人工输入相同的 `InputFrame`，驱动真实角色和互动逻辑。

**完成验收**

- 计数严格从 `0/3` 到 `3/3`，同一晶体不能重复计数。
- 未集齐不能胜利；集齐后出口外观和提示发生变化，到达出口可胜利。
- 失败、重开、返回菜单不会残留上局晶体、陷阱、生命或 Demo 状态。
- 静音/音量控制实际有效，至少一种游戏动作具有清楚可听反馈。
- Demo 一键开始，无后续输入；至少完整挖掘一次，并通过真实逻辑完成三枚收集、开门和胜利。视频可以剪辑展示关键片段，但提交游戏中的 Demo 必须完整可用。
- Demo 可退出或重开，结束后可开始正常人工游玩；不是视频、瞬移或直接改计数。

### D：视觉资源与素材合规

**主要任务**

1. 在不阻塞灰盒的前提下，提供一页视觉规范：原创角色轮廓、服装配色、遗迹材质、晶体颜色、出口状态和危险提示色。
2. 给 B 提供几何体角色拆分和动作参考，给 A 提供模块化墙体/石柱/地面参考，给 C 提供晶体与陷阱视觉反馈参考。
3. 优先建议 Three.js 程序生成几何体、颜色、灯光和 Web Audio；如使用外部素材，必须确认许可、保存来源、作者、许可和本地路径。
4. 可选制作小型本地资源，但不引入复杂 Blender/骨骼管线作为必需依赖；任何外部模型都必须先完成导入样板验证。
5. 维护 `assets/README.md` 和报告所需的素材归属信息，检查文件体积、相对路径、大小写和离线可用性。
6. 进行至少一次视觉可玩性检查：角色是否清楚、宝物是否能与地面区分、危险是否可识别、出口开启前后是否明显不同。

**边界**

- D 不直接修改 A/B/C 的核心模块。建议通过“视觉规范 + 独立资源 + 具体修改建议”交付，由文件拥有者集成。
- D 不承诺未实际导入验证的模型、动画或音效。
- 不使用《古墓丽影》等商业游戏的角色、服装复刻、地图、音乐、模型、标志或剧情文本。

### E：质量、试玩与交付

**主要任务**

1. 建立测试矩阵和缺陷表，记录版本、浏览器、步骤、期望、实际、负责人和复测结果。
2. 协调五人各自运行游戏并留下真实检查记录，避免只有 C 会玩、只有 A 会启动。
3. 在灰盒闭环和候选交付版本上组织测试；AI 可帮助列技术测试项，但实际结果必须来自真实运行。
4. 组织至少一名非本注册小组成员进行外部试玩，只给正常起始信息和操作，不全程指导。
5. 组织两轮改进，至少一轮源于外部试玩；相关观察、原话和记录属于 NO AI，必须由团队亲自完成。
6. 维护 README 和提交清单：操作、精确运行步骤、已测浏览器、声音、Demo、已知限制、素材来源。
7. 统筹 5 分钟以内视频：先确定 15–25 岁范围内更具体的目标玩家细分，再面向“只看视频的平台推广评审委员会”组织团队与游戏介绍、玩家收益、真人操作片段、游戏内 Demo、真实反馈与改进证据，而不是只罗列功能。
8. 从最终提交副本重新解压/打开，按 README 启动，检查文件名、路径和提交历史。

**NO AI 红线**

E 可以协调和保管记录，但不得让 AI 生成、翻译、改写或润色外部试玩观察、测试者原话、两轮改进记录和个人学习总结。不得虚构测试、贡献、结果或许可。

**外部试玩与迭代的最低合规字段（均由团队亲自完成）：**

- 测试者必须不是本注册小组成员；只提供正常开始信息和操作，不先教其路线，只有无法继续时才帮助。
- 明确目标玩家细分，记录匿名测试者标签、大致年龄段、一般角色/情境、游戏频率或经验、对同类游戏的熟悉程度，以及其是否符合目标细分。
- 取得纳入匿名资料和笔记的许可；不得记录姓名、精确年龄、学校、雇主、班级、学号、联系方式或无关敏感信息。
- 记录真实日期、测试者尝试内容、团队直接观察、测试者原话或忠实笔记；不得事后编造更“好看”的反馈。
- 未经明确许可不得录音、录像或拍照。试玩视频不是必交材料，即使获得许可录制，也不得放进本次提交包。
- 两轮改进均写明亲身观察、实际改动、AI 帮助（如有）、执行/检查人和复测结果；至少一轮从这次外部试玩开始，保留有决策价值的失败或部分成功尝试。

**视频与提交隐私：**只录制同意参与的人，不展示密码、私信、无关个人信息或他人屏幕；只由一名成员提交一份小组 MP4，其他成员不重复提交。可选的外部 AI agent playtest 不属必做，不能替代真人片段或游戏内 Demo。

### 3. 修改纪律

- 不两人同时修改同一文件，不让 AI 执行“顺手重构所有文件”。

## 六、接口契约总则：开始并行编码前必须冻结

### 1. 共同技术约定

- 使用原生 JavaScript ES Modules 和 Three.js，不使用 TypeScript、Godot 或 GDScript。
- Three.js 版本、导入方式和运行命令由 A 在骨架期固定；所有人使用同一依赖版本和 lockfile。运行所需 Three.js 与资源应随项目本地提供或打包，不把 CDN、在线 AI 或远程服务作为游戏运行依赖。
- 坐标采用 Three.js 约定：**Y 轴向上，地面为 `y = 0`，1 单位约等于 1 米，角色初始前方为 `-Z`**。
- 位置配置统一写 `[x, y, z]` 数组；进入模块后可转为 `THREE.Vector3`，不要在不同模块混用未说明的对象格式。
- `dt` 单位为秒，主循环建议限制为 `Math.min(clock.getDelta(), 0.05)`，避免切回页面时穿透。
- 所有速度单位为“单位/秒”，所有角度为弧度；相机和角色朝向变量统一命名 `yaw`。
- 模块不得自行创建第二个 renderer、第二个主循环或第二套游戏状态。
- 除了 A 的 `main.js`，其他模块不得自行启动 `requestAnimationFrame`。
- 公开快照中的位置应为副本或按只读处理；其他模块不得通过快照直接改写角色位置。
- 每个模块提供 `reset()` 或 `dispose()`（适用时）；重新开始不得重复注册 DOM 事件或创建无限增长的音源/物体。

### 2. 状态与事件命名

```js
// config.js：只允许 C 的状态机修改当前游戏状态。
export const GAME_STATE = Object.freeze({
  MENU: 'MENU',
  PLAYING: 'PLAYING',
  PAUSED: 'PAUSED',
  WIN: 'WIN',
  GAME_OVER: 'GAME_OVER',
});

export const GAME_MODE = Object.freeze({
  HUMAN: 'HUMAN',
  DEMO: 'DEMO',
});

export const PLAYER_ACTION = Object.freeze({
  IDLE: 'idle',
  WALK: 'walk',
  RUN: 'run',
  JUMP: 'jump',
  FALL: 'fall',
  LAND: 'land',
  COLLECT: 'collect',
  HURT: 'hurt',
  VICTORY: 'victory',
});

export const GAME_RULES = Object.freeze({
  maxHealth: 3,
  interactRadius: 1.8,
  collectDuration: 0.9,
  hurtInvulnerability: 1.0,
  demoTimeout: 120,

```

事件名称采用小写字符串，最低集合为：

```text
step, jump, land, dig, collect, hurt, exit_locked,
exit_open, win, game_over, ui_click
```

A 的主循环只负责把事件交给音频/UI，不根据事件擅自修改 C 的游戏状态。

### 3. 状态迁移契约

| 当前状态 | 允许触发 | 下一状态 | 必须附带的行为 |
|---|---|---|---|
| `MENU` | Start | `PLAYING + HUMAN` | 完整重置，解锁音频，接收人工输入 |
| `MENU` | Watch Demo | `PLAYING + DEMO` | 完整重置，解锁音频，显示 Demo 标识 |
| `PLAYING` | Pause | `PAUSED`，保留原模式 | 停止角色、玩法、陷阱和 Demo 计时 |
| `PLAYING` | 生命归零 | `GAME_OVER` | 停止控制输入，播放失败反馈 |
| `PLAYING` | 出口已开且角色到达出口 | `WIN` | 停止控制输入，播放胜利反馈 |
| `PAUSED` | Resume | `PLAYING`，恢复原模式 | 清空残留输入后继续，不重置本局 |
| `PAUSED/WIN/GAME_OVER` | Restart | `PLAYING`，保留或明确重选模式 | 必须走完整重置流程 |
| 任意非菜单状态 | Menu/退出 Demo | `MENU` | 停止 Demo 和持续音，清理输入与临时提示 |

- `session.state` 是唯一界面与流程依据，DOM 是否显示菜单不能反过来成为第二份状态。
- 非法迁移应忽略并在开发环境给出警告，不能同时出现 `WIN` 和 `GAME_OVER`。
- 切换浏览器标签页或窗口失焦时至少清空输入；人工模式可自动暂停，恢复后须由玩家明确继续。

### 3. 输入模块：B 拥有 `input.js`

```js
export function createInput(targetElement) {
  return {
    readFrame(),       // 每帧调用一次，返回新的 InputFrame
    reset(),           // 清空按键和边沿状态，防止重开后卡键
    setEnabled(flag),  // 仅开关角色移动/互动输入；暂停、取消等全局按键仍需可用
    getLastDevice(),   // 'keyboard' | 'mouse' | 'gamepad'
    dispose(),         // 移除事件监听
  };
}
```

```js
// InputFrame：人工输入与 Demo 输入必须完全同构。
{
  moveX: 0,             // [-1, 1]，右为正
  moveY: 0,             // [-1, 1]，前为正
  lookX: 0,             // 本帧镜头水平角度增量，单位弧度，已在输入源内处理灵敏度
  lookY: 0,             // 本帧镜头垂直角度增量，单位弧度，已在输入源内处理灵敏度
  jumpPressed: false,   // 仅按下边沿为 true
  interactPressed: false,
  sprintHeld: false,
  pausePressed: false,
  confirmPressed: false,
  cancelPressed: false,
}
```

- `Pressed` 是边沿事件，不是持续按住状态；同一帧内 B 和 C 读取的是同一个输入对象，但任何模块都不得把它改写成另一套含义。
- 鼠标增量和手柄摇杆分别在输入源内转换为本帧角度增量；相机应用时不得再次乘鼠标灵敏度。移动使用 `dt`，离散的鼠标角度增量不重复乘 `dt`。
- `window.blur`、页面隐藏和重开时清空按键、鼠标累积量及手柄边沿，防止角色持续移动。
- 手柄若实现，在 `input.js` 内完成死区（建议 0.15）和按钮映射，输出仍只有上述结构。
- UI 按钮通过回调操作，不伪造键盘事件；Demo 则直接返回同构输入帧。

### 4. 角色模块：B 拥有 `player.js`

```js
export function createPlayer({ scene, spawn }) {
  return {
    group,                         // THREE.Group，已加入 scene
    reset(spawn),                  // 唯一允许外部重置角色位置的常规方法
    update(dt, input, world),      // 返回 PlayerEvent[]，不返回计数或生命
    getSnapshot(),                 // 返回 PlayerSnapshot
    playAction(name, duration, options = {}),
    dispose(),
  };
}

// update 的 world 参数：
{
  colliders,       // A 提供的 StaticCollider[]
  cameraYaw,       // B 的相机模块提供
  bounds,          // LEVEL.bounds
  playerRadius,    // LEVEL.playerRadius，XZ 平面碰撞半径
}

// getSnapshot() 返回：
{
  position,        // THREE.Vector3 副本，脚底地面位置
  yaw,
  speed,
  grounded,
  action,          // 当前 PLAYER_ACTION
  controlLocked,   // 挖掘等动作期间是否锁定移动
}
```

`playAction(name, duration, { lockMovement = false } = {})` 只控制视觉与移动锁，不直接收集宝物、扣血或胜利。

`PlayerEvent` 最低格式：`{ type: 'step' | 'jump' | 'land' }`。B 不发 `collect/win` 等玩法事件。

**禁止事项：**C 和 Demo 不得直接写 `player.group.position`、直接修改 `speed` 或瞬移角色；重开统一调用 `reset(spawn)`。

### 6. 游戏会话模块：C 拥有 `gameplay.js`

```js
export function createGameSession({ scene, level }) {
  return {
    start(mode),             // 初始化本局内部实体，mode 为 HUMAN 或 DEMO
    restart(),               // 保留当前模式，完整重置本局
    returnToMenu(),
    togglePause(),
    update(dt, input, playerSnapshot, playerApi), // 返回 GameEvent[]
    getSnapshot(),
    dispose(),
  };
}
```

```js
// getSnapshot() 至少返回：
{
  state,                 // GAME_STATE
  mode,                  // GAME_MODE
  collected,             // 0..3
  total: 3,
  health,
  maxHealth,
  exitOpen,
  objective,             // 给 HUD 的当前目标文本
  interactionPrompt,     // 无提示时为 ''
  resultMessage,
  treasures: [           // 供 Demo 和调试使用；UI 不必全部显示
    { id, state, position } // position 为只读副本
  ],
  exit: { position, open },
}
```

```js
// GameEvent 最低格式：
{ type: 'dig' | 'collect' | 'hurt' | 'exit_locked' |
        'exit_open' | 'win' | 'game_over' }
```

**职责边界：**

- C 可以调用 `playerApi.playAction()`，但不可改写 B 的内部位置或动画变量。
- C 独占晶体、陷阱、生命、计数、出口和状态数据；B 不另存一份计数，A 不根据场景猜测是否胜利。
- 收集必须以距离、状态、真实 `interactPressed` 和动作流程为条件；只靠近不自动增加计数。
- `total` 必须取自 `level.treasures.length`，本项目冻结为 3；`maxHealth` 等规则读取 `GAME_RULES`，不得在其他文件复制不同数值。
- 一次收集的固定顺序为：玩家在 `interactRadius` 内且目标为 `IN_RANGE` → 收到一次 `interactPressed` → 状态改为 `COLLECTING`，发送一次 `dig`，并调用 `playAction('collect', collectDuration, { lockMovement: true })` → C 用本局游戏时间等待 `collectDuration` → 晶体完成升起/发光/旋转后仅一次改为 `COLLECTED` → 更新计数并发送一次 `collect` 事件。
- `COLLECTING` 期间再次按 E 不得重开收集或重复计数；暂停时计时冻结，恢复后继续。若设计允许受伤打断，必须由 C 明确取消并回到 `IN_RANGE`，不能出现动画取消但最终重复结算。
- 陷阱伤害须使用无敌间隔 `hurtInvulnerability`，角色停留在活动陷阱中也不能每帧扣血；生命到 0 只触发一次 `GAME_OVER`。
- 未集齐时进入出口区域只发提示/锁定事件（需限频），集齐时只触发一次 `exit_open`；出口已开且进入出口区域后只触发一次 `WIN`。
- `collectibles.js`、`hazards.js`、`exit.js` 是 C 的内部模块，由 `gameplay.js` 统一创建、重置和更新；它们不得各自操作 DOM、创建主循环或直接切换 `GAME_STATE`，而是通过返回值/事件交给 C 的会话状态机。
- 重开必须重置所有晶体、陷阱相位、收集计时、无敌时间、生命、出口、提示和事件残留；`start/restart` 必须幂等，不得重复添加场景对象。

### 9. Demo 模块：C 拥有 `demo.js`

```js
export function createDemoController({ level, session }) {
  return {
    reset(),
    readFrame(playerSnapshot, cameraYaw), // 用当前相机朝向把世界路径方向转换为 InputFrame
    isFinished(),
    stop(),
  };
}
```

`cameraYaw` 是必需参数：路径点是世界坐标，而 `moveX/moveY` 是相对相机的输入。Demo 必须先计算目标与角色的世界方向，再用当前 `cameraYaw` 转换成输入，不能假定相机永远朝向固定方向。互动/等待收集时移动输入归零，镜头可以保持稳定。

Demo 每步都有完成条件和超时；全局超时读取 `GAME_RULES.demoTimeout`。进入 `WIN/GAME_OVER` 后停止产生移动和互动输入，由主流程显示结果或返回菜单；暂停时不得推进路径索引和计时。

**Demo 唯一允许的调用链：**

```text
LEVEL.demoRoute + 当前真实快照 + 当前 cameraYaw
        ↓
DemoController 生成 InputFrame
        ↓
PlayerController 正常移动 / 相机正常跟随
        ↓
GameSession 正常距离检测、互动、陷阱、计数和出口判断
        ↓
真实 WIN / GAME_OVER / 超时退出
```

**明确禁止：**

- 直接调用内部收集函数跳过距离与按键条件；
- 直接设置 `collected = 3`、`exitOpen = true` 或 `state = WIN`；
- 把角色逐点瞬移，或在镜头外瞬移后声称完成自动游玩；
- 播放 MP4、GIF、预录操作或另一套专门伪造状态的动画；
- 因路线失败仍把 Demo 标为“通过”。

可设置合理超时和卡住检测；触发时应停止 Demo、返回菜单并记录缺陷，而不是伪造成功。

## 八、主循环与启动/重开契约：A 负责组合

### 1. 模块创建顺序

所有工厂和事件监听在应用生命周期内只创建/注册一次；重开调用 `reset/start`，不重新执行整段创建代码。

```js
const environment = createEnvironment(container);
const input = createInput(environment.renderer.domElement);
const player = createPlayer({
  scene: environment.scene,
  spawn: LEVEL.spawn,
});
const followCamera = createFollowCamera({ aspect: width / height });
const audio = createAudio();
const session = createGameSession({
  scene: environment.scene,
  level: LEVEL,
});
const demo = createDemoController({ level: LEVEL, session });
const ui = createUI({
  onStart: () => startRun(GAME_MODE.HUMAN),
  onDemo: () => startRun(GAME_MODE.DEMO),
  onPause: pauseRun,
  onResume: resumeRun,
  onRestart: restartCurrentRun,
  onMenu: returnToMenu,
  onVolumeChange: (value) => audio.setVolume(value),
  onMute: () => audio.toggleMute(),
});
followCamera.reset(player.getSnapshot());
// startRun/pauseRun/resumeRun/restartCurrentRun/returnToMenu 由 A 在 main.js 定义。
```

`createGameSession()` 完成时的初始状态必须为 `MENU`、默认模式为 `HUMAN`，并提供可渲染的空进度快照；场景不能一上来就绕过菜单自动开局。A 在此之后注册一次 resize、全局按钮和键盘处理，再启动唯一的 `animate()`。

### 2. 共同启动流程

人工开始和 Demo 开始必须复用同一个重置流程，只有输入来源不同：

```text
点击 Start 或 Watch Demo
→ audio.unlock()，并处理可能的 Promise 拒绝
→ input.reset() + audio.reset()
→ environment.reset()
→ player.reset(LEVEL.spawn)
→ camera.reset(player.getSnapshot())
→ session.start(HUMAN 或 DEMO)
→ demo.reset()（仅 Demo；人工模式则 stop）
→ 本局 elapsed 归零
→ UI 隐藏菜单、显示 HUD；Demo 显示 demo-badge
→ 人工模式按需在点击回调中请求鼠标控制；Demo 不锁定鼠标
→ 进入 PLAYING
```

### 3. 每帧固定顺序

```js
// 伪代码，只规定顺序和依赖，不要求逐字照抄。
const dt = Math.min(clock.getDelta(), 0.05);
const globalInput = input.readFrame();
const sessionSnapshot = session.getSnapshot();

// Esc、Demo 退出按钮等全局命令优先处理。
// HUMAN：角色使用 globalInput。
// DEMO：角色只使用 demo.readFrame(playerSnapshot, cameraYaw)，
//       但全局 Esc/退出按钮仍可中断 Demo。

if (sessionSnapshot.state === 'PLAYING') {
  elapsed += dt; // elapsed 在启动/重开时归零；暂停时不推进。
  const controlInput = sessionSnapshot.mode === 'DEMO'
    ? demo.readFrame(player.getSnapshot(), followCamera.yaw)
    : globalInput;

  const playerEvents = player.update(dt, controlInput, {
    colliders: environment.colliders,
    cameraYaw: followCamera.yaw,
    bounds: LEVEL.bounds,
    playerRadius: LEVEL.playerRadius,
  });

  followCamera.update(dt, player.getSnapshot(), controlInput);

  const gameEvents = session.update(
    dt,
    controlInput,
    player.getSnapshot(),
    player,
  );

  environment.update(dt, elapsed);
  // main 将 playerEvents + gameEvents 分发给 audio/UI。
}

ui.render(session.getSnapshot(), audio.getSnapshot());
environment.renderer.render(environment.scene, followCamera.camera);
requestAnimationFrame(animate);
```

`resize` 监听只注册一次，并同步调用 `environment.resize()` 和 `followCamera.resize()`，更新 renderer 尺寸、像素比、相机 aspect 与投影矩阵。`clock` 和 `elapsed` 由 `main.js` 统一持有；C 的收集、陷阱和 Demo 计时使用游戏更新中的 `dt`，暂停时不能另用墙钟计时继续推进。

### 4. 重开/返回菜单必须做到

UI 的 Restart 不得只调用 `session.restart()`；A 必须在 `main.js` 中执行与开局相同的完整重置流程，并保留当前 HUMAN/DEMO 模式或按明确设计返回菜单。

- 清空输入边沿和按键状态；
- 清空旧事件、提示、结果文本和 Demo 路径索引；
- 角色、相机、晶体、陷阱、生命、出口、声音持续状态全部复位；
- 不重复注册键盘、鼠标、按钮或 resize 监听；
- 不创建第二个 renderer、相机、角色或动画循环；
- Demo 返回菜单后，再点击 Start 必须完全由真人输入控制。

## 九、三人真正并行的执行方法

### 阶段 0：共同冻结，完成后才能并行（建议 2～3 小时）

全员共同完成：

1. 阅读本方案，确认姓名、文件所有权和 P0 范围。
2. A 建立项目骨架、依赖、基础 DOM、模块占位实现和启动说明。
3. A/B/C 一起核对第六至八节，尤其是 `InputFrame`、快照、事件和 `LEVEL`。
4. 用占位角色和占位玩法运行一次主循环，确认导入路径、渲染和按钮骨架正常。
5. 保存一个名为 `contract-freeze` 的提交、平台版本或压缩备份。
6. 此后接口默认冻结；确需改变时必须三人同意并同步修改契约和调用方。

### 阶段 1：三人同时 Vibecoding

| 开发线 | 可独立完成的内容 | 不等待谁 | 必须遵守 |
|---|---|---|---|
| A | 灰盒场景、光照、静态碰撞、坐标和主循环 | 不等待精细角色、最终 UI、音效 | 不改 B/C 文件；占位模块仍保持接口 |
| B | 输入、角色几何体、移动、相机、动作 | 不等待最终场景美术和宝物逻辑 | 只用契约中的 colliders/spawn；不写玩法计数 |
| C | 晶体状态、陷阱、出口、HUD、菜单、音频、Demo 状态机 | 不等待最终角色模型和场景装饰 | 用公开 playerApi 和快照；Demo 不抄一套玩法 |

每个人都可以在自己的版本上启动游戏，因为未完成的其他模块仍是可运行占位实现。**并行的是有契约的模块，不是三个互不知情的完整 HTML 游戏。**

### 阶段 2：小批量集成，而非最后一天大拼接

建议至少进行三次集成：

1. **集成 1：移动闭环。**A 场景 + B 角色/相机 + C 占位 HUD；验证角色能走遍路线。
2. **集成 2：人工玩法闭环。**加入 C 的晶体、陷阱、出口和状态；验证正常胜利、失败、重开。
3. **集成 3：Demo 与声音。**加入自动路线和音频；验证真实逻辑自动通关、可退出、可恢复人工模式。

集成原则：

- A 拉取/合并 B、C 的已测试版本；B/C 先说明改动文件、自测结果和已知问题。
- 出错时按公开接口定位归属，不由 AI 随机重写多个模块。
- 涉及谁拥有的文件，谁确认最终修复；跨模块问题由 A 组织，B/C 共同复测。
- 每次集成后保留稳定版本，再开始下一批功能。
- E 将缺陷录入清单；D 检查视觉与素材，不在集成期临时加入未经验证的大资源。

## 十、Vibecoding 专项工作规范

### 1. 必须承认的团队工作方式

- 五人均以提示词驱动 AI 生成/修改代码为主，不因岗位名称假定有人能独立手写整个系统。
- “会用 AI”不等于结果自动正确；每段保留的代码都必须经过本地运行、浏览器观察和对应验收。
- 组员需要能解释自己模块的基本数据流：输入从哪里来、状态由谁修改、如何触发胜利、Demo 为什么不是伪造。
- 遇到看不懂的代码，应先要求 AI 逐段解释并做小范围验证，不继续堆叠新功能。
- 不把 AI 的“已完成”“应该能运行”“已修复”写成真实测试结果。

### 2. 每次 AI 请求只做一个小任务

推荐粒度：

```text
一个公开方法 / 一个可验收行为 / 一个明确缺陷
```

不推荐：

```text
“把整个游戏一次性生成。”
“重构所有文件并顺便优化。”
“我不知道哪里坏了，你全部修好。”
“绕过接口，先让 Demo 直接显示胜利。”
```

### 3. 每次请求 AI 前必须提供的信息

```text
【课程与技术】
HTML + CSS + JavaScript + Three.js；浏览器本地运行；不使用 Godot。

【当前小任务】
只实现/修复什么，可观察的验收结果是什么。

【我的角色与允许修改的文件】
A/B/C 中哪一条开发线；明确列出允许修改的文件，禁止修改其他成员文件。

【必须阅读的上下文】
粘贴本方案相关接口、当前文件、level/config 的相关定义。

【当前实际行为】
已运行后看到什么；控制台完整报错；复现步骤。

【期望行为】
用输入 → 状态变化 → 可见/可听反馈描述。

【约束】
保留公开接口；不新增第二主循环；不使用远程服务；不瞬移 Demo；
不伪造测试；不一次生成整个项目；如接口不足先提出变更，不擅自修改。

【要求 AI 返回】
1. 修改文件和原因；2. 小范围代码修改；3. 精确运行方式；
4. 手动测试步骤；5. 仍需人工确认的风险。
```

## 十三、范围缩减与风险预案

### 1. 时间不足时可以砍

按以下顺序缩减：

1. 额外装饰、粒子、复杂雾效和贴图；
2. 额外动画、冲刺和复杂跳跃；
3. 手柄支持（若未实测，则如实说明或不列为已支持）；
4. 外部模型和 Blender 管线；
5. 地图尺寸、石柱数量和路线长度。

### 2. 不能砍

- Three.js/JavaScript 核心实现；
- 可控制、可完成、可重开的真实游戏；
- 明确目标和进度/结果反馈；
- 声音与音量/静音；
- 真实游戏内 Demo 及其退出/恢复人工操作；
- 每人贡献和实机检查；
- 外部试玩、两轮改进、学习总结；
- 可运行源代码、README 和不超过 5 分钟的视频。

### 3. 高风险项及预案

| 风险 | 早期信号 | 预案 |
|---|---|---|
| 三人代码无法拼接 | 同名不同义、各自创建 scene/renderer/state | 回到冻结契约；只修接口适配，不让 AI 全项目重写 |
| AI 反复改坏 | 修改范围越来越大、未经运行连续生成 | 回退稳定版，缩小到单个缺陷，提供真实报错 |
| B 成为瓶颈 | 角色不能稳定移动，C 无法联调 | 先用胶囊/方块角色和固定相机，保留输入接口，逐步恢复外观 |
| C 的 Demo 卡住 | 路径点不可达、互动距离不稳定 | A/B/C 在灰盒第 4 天前联调；增加路径容差、卡住检测，禁止瞬移造假 |
| 美术阻塞 | 等模型才能开始程序 | 全部先用几何体；外部资源只作可替换增强 |
| 声音在浏览器无声 | 未点击就播放、远程音频失败 | 用户点击后 unlock，本地生成/本地文件，实测音量和静音 |
| 重开状态污染 | 晶体消失、监听重复、Demo 输入残留 | 按统一启动流程逐项复位，连续重开三次测试 |
| 本地提交版不能跑 | 只在开发环境测试、绝对路径或漏文件 | 提前从 ZIP/提交副本按 README 冷启动 |
| NO AI 内容违规 | 让 AI 整理测试者原话或个人总结 | 由本人用简单语言独立记录，AI 不接触这些内容 |
